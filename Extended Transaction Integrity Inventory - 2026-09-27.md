## Downstream delivery forms

Despatch Advice (Page 161) has 7,568 details and database uniqueness on both `(TNO,SNO)` and `(TNO,ITEMCODE,ITEMSPECIFICATIONCODE)`; it has no monetary footer. Its custom Interactive Grid save process carries an unused local key variable, but the submitted `(TNO,SNO)` is enforced by the database and current rows have neither null nor duplicate keys. No change is justified.

Sales GRN (Page 184) is a different business family from Sales Quotation. Its active client/AJAX calculation derives `AMOUNT` from `REJECTEDQUANTITY1 × RATE`, then derives line footer and total; a generic `QUANTITY1 × RATE` guard would reject valid documents. Historic rows include legacy lines with retained rates/amounts but absent quantities, so the formula cannot safely be applied retroactively. The live AJAX calculation declares `mfactor` but never loads it before deriving secondary/accepted/rejected secondary quantities. A one-query staged repair loads `MAX(ITEMSPECIFICATION.MULTIPLYINGFACTOR)` by the existing item-specification key. It is not deployed: no live item specification currently has a non-null factor, so a positive production-equivalent regression case is unavailable. The page also has 11 line-footer and 2 document-header discrepancies that need a dedicated Sales GRN accounting/footer trace before any final-save reconciliation or verifier.

Job Bill (Page 213) has 494 detail rows with no footer or line-total mismatch. One legacy detail has a null `SNO`, which makes the existing `DELETE` branch (`TNO` plus `SNO`) unable to remove it because SQL null equality never matches. The detail update branch already identifies its row by `ROWID`. A staged, one-line repair uses the same `ROWID` predicate for deletion and was verified to resolve exactly one row for the legacy null-key case. It is not deployed pending authorization. The 72 footer rows that do not map to exactly one current detail need source-document/lifecycle analysis; they must not be deleted or remapped generically.

Freight Advice (Page 199) is currently arithmetically consistent (nine details; zero footer/line-total differences), but it is not transactionally atomic. Its amount-focus and “prepare data” AJAX paths directly delete/rebuild `FREIGHTADVICEDETAIL` and `FREIGHTADVICEDETAILFOOTER` and explicitly commit. Thus cancellation or a later final-save failure can leave durable partial detail/footer state. Because those callbacks also select source transactions and calculate freight, tax, TDS, advance, deduction, and rounding values, removing a commit alone would change its workflow. This is an architecture-level blocker requiring a separately reviewed, non-persisting preview plus final-save design.

Job Bill Pass (Page 221) has a severe delete-path family error: its after-submit `Delete Detail` process is executed by the page's Delete button but deletes `PURCHASEORDERDETAIL`, `PURCHASEORDERDETAILFOOTER`, `PURCHASEORDERFOOTER`, `PURCHASEORDERTAC`, and `PURCHASEORDERFN` instead of Job Bill Pass data. The normal Page 221 replacement path already identifies the intended child family (`JBPASSDETAIL`, `JBPASSDETAILFOOTER`, `JBPASSFOOTER`, source-link children, production links, and TDS details). The staged repair swaps only those target statements; all seven intended SQL statements compiled in a rollback-only test. No historic data is changed. Current orphan counts (74 detail, 40 detail-footer, 38 footer) demonstrate why any historic cleanup must remain a separate approved operation.

Proforma Invoice (Page 383) has a well-constrained detail/footer model: `PINVOICEDETAIL` is keyed by `(TNO,SNO)`, its footer has a parent foreign key and unique footer-head constraint, and database triggers assign absent IDs on insert. All 143 live details agree with the associated footer and total. One document has drift in the basic detail-derived header aggregates, but `PINVOICEAMOUNT` differs from a naive detail total on 36 documents because the header also has marine insurance, adjusted advance, paid/deducted, rounding, TDS, and LC-interest fields. No generic header recalculation or final guard is safe until that established accounting chain is traced.

Rate Contract (Page 714) contains the same wrong-table delete clone as Job Bill Pass: its Page 714 Delete button invokes a `Delete Detail` process that deletes `SALESORDER*` tables instead of Rate Contract children. The staged repair replaces those five targets with `RATECONTRACTDETAILFOOTER`, `RATECONTRACTDETAIL`, `RATECONTRACTFOOTER`, `RATECONTRACTTAC`, and `RATECONTRACTFN`, in child-first order. The statements compiled in a rollback-only test. There are currently no Rate Contract child records, so there is no historic cleanup; the repair prevents future failed/orphaning deletes.

The same source-wide scan found an active wrong-table delete clone on Reimbursement Policy (Page 649). Its form uses `CONVEYANCESCHEME` with the `CONVEYANCESCHEMEDESIGNATION` and `CONVEYANCESCHEMEDETAIL` grids, yet its Delete button targeted five `PURCHASEORDER*` tables. A staged repair deletes only the two actual children, in child-first order; both statements compiled in a rollback-only test. No current child records or orphan records exist. Other cross-table delete snippets found in pages 195, 202, and 312 are disabled cleanup actions or no-op global-ID cleanup paths, not active target-form delete processes, and were left unchanged.

Material Out (Page 168) has legacy detail persistence defects. All 314 current detail rows have null `SNO` values; 306 still have a live header, while eight are orphaned. The Interactive Grid source returns `ROWID`, but the live update branch uses nullable `SNO`, and its delete branch uses the unrelated `:P161_TNO` page item together with `SNO`. Thus existing lines cannot reliably be edited or deleted. A staged repair changes only the update/delete predicates to `(P168_TNO, ROWID)`. All 314 null-key rows have distinct physical row identities, so the repair is precise and does not change stored data. Although the grid's manual-create branch assigns a `GLOBALTNO` line key, the Page 168 and Page 415 “Insert Data into Detail From D.A.” actions both intentionally replace the lines with Despatch Advice lines whose `SNO` is null. Therefore a table-level non-null/unique `SNO` change would break those live workflows and is deliberately out of scope; their line-number lifecycle needs a separately tested redesign. Two detail items no longer match the linked Despatch Advice; that historical source-document discrepancy needs document-level review rather than an automatic rewrite.

## Cross-cutting observation

The recurring pattern is an Interactive Grid/AJAX calculation that persists detail-footer rows before the final document save, followed by a different after-submit footer aggregation. The safe correction pattern is form-specific:

1. Preserve the existing business formula and manual footer values.
2. At final Save, derive stored detail footer/total fields from the submitted footer rows in the same APEX transaction.
3. Derive only those header totals proven by the form’s own existing semantics.
4. Add a final server verifier only after confirming the line/UOM/discount/rounding formula.
5. Never apply this to historic duplicate identities where a footer cannot be unambiguously owned by a line.
